## How this code reaches Dagda

The root and Status are the store's owner, not an ordinary caller, so most of what they touch is the node's
configuration and its figures. Against the bar (Macha calls `dagda::Context` only; a call reachable only through a
`Node` part is a GAP), three facts shape every row:

1. `Context` has no figures, no reload, no activity and no admission noun (CTXH:158-425: Domains, Objects, Claims,
   Leases, Heads, Tickets). Every figure Status and telemetry read (pool used/limit/backends online/degraded, data store
   diagnostics, cache stats, repair diagnostics and gates, prompt replication, the arbiter's stats, the activity
   clocks) is a `Node` part (NH:363-384) or `Node::store()`.
2. The only non-`Node` route to those figures is Dannan's Status surface, which the node fills under `dagda.*` at open
   and then every `NodeOptions::status_interval`, 10 s by default (N:1140-1350, NH:248-249, N:402-403, N:472-479).
   Dannan's `Surface::snapshot()` (`../dannan/dannan/status/surface.h:25-39`) is readable by Macha. The cutover plan
   says Status reads the accessors live, not the published figures (`TODO/2026-11-13-store-cutover.md` order 4), so
   the surface is a DIFFERS (staleness), not a substitute.
3. Macha's root owns three things Dagda's node builds for itself: the DATA arbiter, the activity clocks and the event
   counts. In Macha each is one object shared by the store, HTTP, torrent and Status (`ns:31`, `sv:43`, `sv:81-82`,
   `ns:258`). Dagda's node makes its own arbiter (N:262-274) and its own clocks (N:231), and reports events on
   Dannan's `NodeEvents` (N:119-121, SS:60, SS:86).
